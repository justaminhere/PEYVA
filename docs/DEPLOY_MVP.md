# Public MVP deployment

Status: code ready and tested in-process (`test/web-public.test.ts`). **Not yet deployed or run on a real platform.** The Docker image has not been built here (no Docker on the development VM), and MrBilit has not been called from a cloud IP.

## 1. Why not GitHub Pages

GitHub Pages serves static files only. PEYVA needs a running server for:
- the Hono API and SSE streaming,
- PostgreSQL,
- the LLM key, which must never reach the browser,
- the MrBilit MCP process,
- the monitoring worker.

GitHub keeps the code. A platform (Render here) builds it from GitHub and runs it.

## 2. What public mode changes (`PEYVA_PUBLIC=1`)

**Who can use it**
- Anyone with the link, without an account.
- Each visitor gets a random id in a signed cookie: `peyva_v`, HMAC-SHA256 with `PEYVA_SESSION_SECRET`, HttpOnly, Secure, SameSite=Lax, 30 days.
- Goals, memory, conversations and alerts are scoped to that id, the same way they were scoped to the single local user.
- A forged or changed cookie is ignored, and the request becomes a new, empty visitor.
- Clearing cookies loses that visitor's data. There is no login or recovery.

**Network**
- The server listens on `0.0.0.0:$PORT` behind the platform's HTTPS proxy.
- Only `PEYVA_PUBLIC_HOST` (or Render's `RENDER_EXTERNAL_HOSTNAME`) is accepted as Host. Write requests also need the origin `https://<host>`.
- `GET /api/health` answers for any Host, so the platform health check works. It reveals nothing.

**Sessions**
- One serialized agent session per visitor, held in memory: at most 200, dropped after 30 idle minutes.
- A dropped session resumes from PostgreSQL on the visitor's next request.

**Quotas**
- They are kept in memory and reset at a restart and at UTC midnight.
- Each limit below can be changed with its environment variable.

| Limit | Default | Variable |
|---|---|---|
| Chat messages per visitor per day | 25 | `PEYVA_PUBLIC_TURNS_PER_DAY` |
| Manual searches («جست‌وجوی دوباره») per visitor per day | 10 | `PEYVA_PUBLIC_SEARCHES_PER_DAY` |
| LLM tokens per day, whole site | 150,000 | `PEYVA_PUBLIC_TOKENS_PER_DAY` |
| LLM turns at the same time | 2 | `PEYVA_PUBLIC_CONCURRENT_TURNS` |
| New visitors per IP per day | 5 | `PEYVA_PUBLIC_NEW_VISITORS_PER_IP` |
| Active monitoring goals per visitor | 2 | `PEYVA_PUBLIC_GOALS_PER_VISITOR` |
| Active monitoring goals, whole site | 40 | `PEYVA_PUBLIC_GOALS_TOTAL` |

How quotas are enforced:
- A refused request gets a Persian reason, and the UI shows it.
- A chat message refused before it starts goes back into the input box.
- Quotas are checked before any LLM or provider call.
- The token count comes from the provider's reported usage for each turn.
- The client IP is the last entry of `X-Forwarded-For` (the one the platform's proxy adds). Another header can be set with `PEYVA_CLIENT_IP_HEADER`.

**Other behaviour**
- **Worker:** runs inside the web process by default (`PEYVA_EMBEDDED_WORKER=0` turns it off), with the same 6-hour minimum interval.
- **Telegram:** off. Linking was a single-user CLI flow, so alerts appear in the web app only.
- **Banner:** the UI shows the limits and asks visitors not to enter personal data.

**Unchanged in local mode:** `bun run peyva:web` still refuses non-loopback addresses and still has no cookies or quotas.

## 3. Deploy on Render

1. Push the repository to GitHub, after `bun run check:secrets`.
2. In Render, go to New, then Blueprint, and pick `justaminhere/PEYVA`. Render reads `render.yaml` and creates:
   - **Web service `peyva`:** Docker, Frankfurt, plan `starter`, health check `/api/health`.
   - **PostgreSQL `peyva-db`:** Frankfurt, plan `basic-256mb`, version 18.
3. Render asks for `PEYVA_LLM_BASE_URL`, `PEYVA_LLM_API_KEY` and `PEYVA_LLM_MODEL`.
   - Use the same values as your `.env`, but **create a new Groq key** for the server.
   - `PEYVA_SESSION_SECRET` is generated by Render. The database URL is wired automatically.
4. The first deploy builds the image. It also pre-installs `mrbilit-mcp==0.5.2` with uv.
5. Migrations run at start. The log line `PEYVA public MVP listening on … for peyva-….onrender.com` means it is up.
6. For a custom domain, add it in Render and set `PEYVA_PUBLIC_HOST=peyva.example.com,peyva-….onrender.com`.

**Cost.** Render charges for the always-on `starter` web service and the `basic-256mb` database. Check current prices in Render before creating them.
- The free web plan sleeps when idle, and the worker would sleep with it.
- The free database expires.
- Either is fine for a one-day demo, but not for monitoring.

**Other platforms.** The same `Dockerfile` works on Railway or Fly.io. You need:
- a PostgreSQL URL in `PEYVA_DATABASE_URL`,
- `PEYVA_PUBLIC_HOST`,
- `PEYVA_SESSION_SECRET` (`openssl rand -base64 48`),
- the three LLM variables,
- the platform's `PORT`.

## 3b. Deploy on Liara (Iran)

Liara runs the app from an Iranian IP.

**What works and what doesn't from an Iranian server**
- **MrBilit:** more likely to work.
- **Groq:** will not work, because it blocks IP ranges from sanctioned countries. Do not route it through a proxy or VPN.
  - Use an OpenAI-compatible LLM endpoint that serves Iran, for example Liara's AI service.
  - The model must support tool (function) calling and handle Persian.
  - Check both with `bun run peyva:llm-check` before deploying.
- **Telegram:** blocked from Iran. That changes nothing here, because Telegram is off in public mode.

**Steps**
1. In the Liara console:
   - Create a **Docker** app, e.g. `peyva`.
   - Create a **PostgreSQL** database on the same private network.
2. Set the app's environment variables:
   - `PEYVA_PUBLIC=1`
   - `PEYVA_PUBLIC_HOST=peyva.liara.run` (the app's real domain)
   - `PEYVA_SESSION_SECRET` (`openssl rand -base64 48`)
   - `PEYVA_DATABASE_URL`: the database's private-network URL
   - `PEYVA_LLM_BASE_URL`, `PEYVA_LLM_API_KEY`, `PEYVA_LLM_MODEL`: from the Liara AI panel
3. Deploy from the repository folder with `liara deploy --app peyva --platform docker --port 10000`. The port must be 10000, which is the public-mode default when the platform sets no `PORT`.
   - `.liaraignore` keeps `.env`, `node_modules`, local data and logs out of the upload.
4. The Dockerfile takes Python from Debian and uv from PyPI, not from GitHub or ghcr.io, because those may be unreachable from Iranian build servers. If a build step still cannot download something, report the failing line; do not add mirrors of unknown origin.
5. Check the client IP header. The new-visitor cap counts by the last `X-Forwarded-For` entry. If Liara's proxy puts its own address there, every visitor shares one "IP" and the 6th new visitor of the day is refused.
   - Test from two different networks (mobile data and Wi-Fi).
   - If the second is refused, set `PEYVA_CLIENT_IP_HEADER` to the header Liara uses for the real client IP, or raise `PEYVA_PUBLIC_NEW_VISITORS_PER_IP`.

## 4. Before calling it working, check on the deployed site

1. `/api/health` returns `{"ok":true}`.
2. The first visit sets the `peyva_v` cookie, and the banner shows.
3. A full scenario works on the real site: Tehran to Kish, dates, budget, real results.
   - **Risk:** MrBilit might refuse or time out from a datacenter IP.
   - The spike's sandbox run failed because of that sandbox's DNS, not MrBilit; from the developer's own connection it works.
   - If MrBilit fails from Render, the app reports a provider error. **Do not route around it with a proxy** (project rule).
   - Report the error. A server in another region is a legitimate option to try.
4. A second browser (private window) sees none of the first visitor's goals.
5. Approve a monitoring goal. The log shows `worker: goal #N …` after the first check.
6. Watch the Groq usage page for a day. The site's token cap must stay below the key's daily limit.

## 5. Security notes and known limits

- **Secrets.** A real Groq key was found in 13 unpushed commits: a stray file named `\`, a copy of `.env` from 2026-11-20.
  - Those commits were rewritten before any push, so the key never reached GitHub.
  - The key did appear in a development tool's output, so **rotate it** in the Groq console.
  - `bun run check:secrets` now checks tracked files and unpushed commits before each push.
- **Anonymous public data.** The operator can read every visitor's chats in PostgreSQL and in the container's session logs. The banner tells visitors not to enter personal data. Before inviting real users, add a short privacy note.
- **Quotas are in memory.** With more than one instance they would be per instance; this blueprint runs one. A restart resets the daily counts.
- **No way to stop a long turn**, and no admin page. The Groq free tier allows about 5–8 full conversations per day for the whole site.
- **Fixes in the code, not yet verified on a platform:** the Dockerfile, the uv cache as a non-root user, and Render plan names. Review the first build log.
